# Доступность и доставка сообщений: 27 ноября 2026

Входящие сохраняются в журнале шлюза, затем в очереди интеграции и в Chatwoot. Подтверждение получения и завершения обработки раздельные; необработанные события и связанные файлы не удаляются очисткой. Неопределённый результат исходящей отправки сверяется по журналу и идентификатору операции, а не отправляется повторно вслепую.

## Исправления

- Ответ клиента в MAX теперь проходит проверку очереди даже тогда, когда контакт ранее появился из исходящего сообщения обычного приложения MAX. Неизвестный клиент без владельца попадает в «Неназначенные». Существующие назначения, ранее принадлежавшие менеджеру приватные контакты и ограниченные диалоги ботов автоматически не раскрываются.
- Если телефон известен, входящий проверяется в CRM. При совпадении назначается сопоставленному активному менеджеру без смены ответственного в Bitrix24. Если совпадения или сопоставленного сотрудника нет, новый входящий становится доступен в общей очереди. Последующие входящие позволяют повторить предыдущий поиск, который ничего не нашёл. При недоступности CRM сохраняется штатный повтор попыток; сообщения сохраняются, но назначение может задержаться.
- Завершившееся соединение MAX восстанавливается по сохранённой сессии с задержкой между попытками. При отзыве авторизации требуется штатное повторное подключение; шлюз не запускает QR/ввод пароля самостоятельно. Зависший цикл синхронизации ограничен по времени и виден в проверке здоровья.
- Индикатор руководителя учитывает подключение/синхронизацию MAX и время последней успешной обработки worker, а не только наличие запущенного процесса. Входящая очередь включает ожидающие медиа обоих каналов.

Для однократного восстановления пропущенной маршрутизации после обновления:

```sh
bash scripts/compose.sh exec -T -e CONFIRM_INBOUND_RECOVERY=approved chatwoot-web bundle exec rails runner - < scripts/server/recover-inbound-routing.rb
```

Обрабатывается не более 100 контактов без владельца. Ограничения приватности проверяются тем же сервисом, что и для новых входящих. Выводятся только количества; сообщения не отправляются.

## Автоматический контроль на сервере

`pravburo-chatwoot-watchdog.timer` запускает проверку каждую минуту. Проверяются основной и резервный HTTPS, контейнеры, соединения мессенджеров, очереди и свежесть worker. Отчёт без переписок и телефонов: `.state/watchdog/status.json`; журнал: `journalctl -u pravburo-chatwoot-watchdog.service`.

Только после трёх последовательных проверок `unhealthy` перезапускается один работающий сервис приложения. Повторный перезапуск того же сервиса разрешён не чаще чем раз в 10 минут; лимит сохраняется до попытки восстановления. Базы данных, host nginx, остановленные оператором контейнеры и другие проекты не перезапускаются. Ошибки внешнего провайдера и неопределённые отправки показываются как проблемы, но отдельные сообщения не переотправляются.

`pravburo-chatwoot.service` включает запуск существующих образов приложения после запуска Docker при загрузке VPS. Новые образы при загрузке не скачиваются и не собираются. Во время установки старт уже работающего стека повторно не выполняется.

Для обслуживания: `touch .state/watchdog/paused`; после завершения: `rm .state/watchdog/paused`. Это приостанавливает контроль, а не останавливает приложение. Проверка без перезапусков: `python3 scripts/server/watchdog.py`.

## Резервный вход для Safari

Доступен `https://162.248.166.241:18443/app/login`: обычная авторизация, проверяемый публичный сертификат на IP, WebSocket и защищённые файлы. Основной домен и резервный вход по домену сохраняются. Новый порт не открывался: используется ранее согласованный 18443.

Внешняя проверка WebKit по домену зависала до получения HTTP-страницы, в том числе с отключённой только для диагностики проверкой сертификата. На том же IP без SNI соединение устанавливалось. Это указывает на различие обработки TLS на маршруте, но не устанавливает конкретного виновника. IP-вход прошёл Chrome и WebKit с обычной проверкой сертификата. Доступность доменного входа в Safari пока не подтверждена.

Изолированный официальный Certbot закреплён digest в `infra/certbot-ip.image`; состояние и ключи находятся в `secrets/acme-ip`, тестовый ACME использует отдельный каталог. Системный Certbot не меняется. `pravburo-chatwoot-ip-renew.timer` проверяет продление каждые два часа; nginx перечитывается только после изменения сертификата. Перед активацией пройдена staging-проверка; недоверенный staging-сертификат не устанавливался. HTTP-vhost на IP обслуживает ACME; именные виртуальные хосты других приложений не изменяются.

Установка: `python3 scripts/server/configure-ip-fallback.py`, затем `python3 scripts/server/install-watchdog.py`. Watchdog также проверяет HTTPS по IP. Ключи и ACME-состояние не попадают в Git.

## Проверки обновления

98 Rails-примеров разграничения доступа/маршрутизации, 43 теста MAX, 21 тест интеграции, 23 теста компонентов интерфейса и 6 тестов политики восстановления прошли. Браузерная проверка IP-входа проверяет загрузку в Chrome/WebKit; отдельная проверка менеджера — авторизацию, WebSocket, телефонную форму без реального поиска/отправки и повторную отметку чтения.

После установки: 12 контейнеров здоровы, Telegram/MAX подключены, очереди входящих/исходящих пусты. Однократное восстановление рассмотрело 13 контактов: один допущен в неназначенную очередь, для пяти поставлен повторный CRM-поиск. Эти значения — результат проверки, а не постоянная гарантия состояния.

## Границы

На одном VPS нет отказоустойчивости при полном отказе VPS/диска/датацентра. Владелец выбрал укрепление текущего сервера; второй сервер не настраивается. Контроль с самого сервера не доказывает доступность маршрута каждого оператора/VPN. Проверки браузеров фиксируются отдельно от серверного HTTPS. Автоматизация и внешнее хранение резервных копий остаются вне согласованного объёма.

Переписки и медиа не отправляются внешним сервисам мониторинга. Для проверки не отправляются сообщения реальным клиентам.
