# Аудит корпоративного мультимессенджера — 25.11.2026

Проверены собственные изменения Chatwoot CE, Telegram gateway, Django delivery/CRM, модель доступа, интерфейс CRM, Compose и рабочая установка `mess.prav-buro.ru`. MAX исключён по решению владельца. Основное ТЗ дополнено решениями Telegram-first и Bitrix24/shared intake; общая очередь скрытых номеров сама по себе не является нарушением изоляции.

**Вывод: для широкой эксплуатации остаются 6 замечаний P1 и 4 P2.** Работоспособность HTTP и зелёные штатные тесты не закрывают обнаруженные сценарии отказа. Прямого обхода ownership в проверенных штатных сценариях не выявлено; отказ аварийного отключения сотрудника является отдельным дефектом безопасности.

Аудит выполнен без исправлений рабочего кода и развёртывания обновления. В отдельном последующем поручении созданы два менеджера и сопоставления CRM; это эксплуатационное действие, не исправление результатов аудита. Клиентские сообщения не отправлялись, сделки для тестов не изменялись, производственные переписки и сессии не копировались в лабораторию.

## Доказательства и приоритеты

P1 — исправить перед расширением использования: риск потери переписки, сохранения доступа или невосстановимости. P2 — исправить следующим набором: согласованность, интерфейс и эксплуатационная устойчивость. Все замечания ниже открыты, не приняты владельцем как допустимый риск.

### A01 · P1 · Входящие документы/фото могут терять вложение из-за имени файла

`gateways/telegram/tg_gateway/driver.py:163`: результат `download_media` игнорируется. Telethon дописывает расширение, когда передан путь без него; gateway проверяет существование исходного `attachment-UUID`, хотя фактический файл — `attachment-UUID.pdf`. Корректный небольшой PDF получает `attachment_too_large`, список attachments остаётся пустым, фактический файл остаётся без привязки. Проверены код установленной Telethon и синтетическое получение PDF с её настоящим `_get_proper_filename`.

Исправление: сохранять в заранее открытый контролируемый файл/поток либо корректно использовать возвращённый путь, согласовав его с endpoint скачивания и удалением. Проверить PDF, JPEG, OGG и повтор после рестарта. Не ограничиваться mock, который всегда пишет ровно в переданный путь.

### A02 · P1 · Неопределённая отправка блокирует отключение менеджера

`chatwoot/app/services/corporate/staff_service.rb:21`: сначала передаются клиенты и только затем отзывается доступ. `OwnershipService` запрещает передачу при `in_flight`/`unknown` Telegram или CRM. Исключение откатывает всю транзакцию отключения; membership остаётся активным, прежний менеджер продолжает читать свои чаты. Воспроизведено через реальный service и проверку `Corporate.can_read?`.

Исправление: отзыв роли/сессий должен быть немедленным и независимым от завершения доставки; последующая передача истории и reconciliation выполняются отдельно с аудитом. Проверить также CRM unknown, открытый WebSocket и медиасессию.

### A03 · P1 · Вложения доступны до антивирусной проверки; заметки её обходят

`chatwoot/app/builders/messages/message_builder.rb:39`, `chatwoot/app/controllers/api/v1/corporate_files_controller.rb:3`, `integration/delivery/worker.py:115`. Файл сохраняется в сообщение и доступен авторизованному читателю сразу. Для исходящих антивирус включается позже в delivery worker; для private note операция доставки вообще не создаётся, поэтому проверки содержимого нет. Поддерживаемый MIME проверяется по объявленному значению, без полноценного карантина.

Локальный request probe создал private note со стандартным безопасным тестовым EICAR-файлом и скачал его от имени руководителя с HTTP 200. Это не отправлялось на рабочий сервер.

Исправление: единый серверный карантин и состояние проверки для любых вложений, включая заметки/direct uploads; выдача, превью и пересылка только после успешного сканирования. Недоступность сканера должна закрывать выдачу, а не только внешнюю отправку.

### A04 · P1 · Старые unknown-операции способны заблокировать новые сообщения

Два независимых места:

- `chatwoot/app/controllers/internal/corporate_controller.rb:54`: первые 50 pending/unknown/in_flight по ID возвращаются без курсора. При 50 старых неизвестных результатах новый pending не попадает в выборку ни на следующем опросе, ни после него. Воспроизведено request-тестом с 51 операцией.
- `gateways/telegram/tg_gateway/journal.py:76`: сначала выбираются первые 100 неподтверждённых событий. Если они outgoing и удерживаются из-за unknown того же peer, новые incoming за пределом окна не попадают в выдачу. Два повторных вызова вернули пустой список при наличии нового входящего.

Исправление: независимые очереди/квоты для новых отправок и reconciliation, курсоры/справедливый обход; неоднозначность одного чата не должна останавливать остальные. Не превращать unknown в слепую повторную отправку.

### A05 · P1 · Сбой загрузки медиа оставляет входящее без durable записи

`gateways/telegram/tg_gateway/driver.py:164`: скачивание выполняется до `journal.save_event`. При временном OSError обработчик завершается, в журнале нет даже envelope входящего, своего задания повторного скачивания также нет. Воспроизведены исключение и нулевое число durable событий. Автоматический повтор со стороны Telegram для этого прикладного сбоя не доказан; полагаться на него как на гарантию нельзя.

Исправление: сохранять событие до загрузки, выделить состояния media_pending/media_failed и восстанавливаемые попытки. Ошибку/неподдерживаемое вложение показывать в чате, сохраняя текст. Сейчас `attachment_error` gateway не переносится в видимое состояние сообщения в `Corporate::IngestEvent`.

### A06 · P1 · Резервные копии проекта выполняются вручную и хранятся на том же сервере

Имеются ручные копии и успешные проверки восстановления БД; это положительный результат. Однако собственного расписания проекта нет. Проверенный хостовый `pravburo-services-backup` перечисляет другие приложения и не включает новый Compose project. В `scripts/server/backup.py` нет защищённой внешней выгрузки. Потеря диска/сервера может уничтожить и данные, и все эти копии; интервалы между ручными запусками не ограничены.

Исправление: расписание, контролируемое внешнее зашифрованное хранение, retention, уведомление об ошибках и регулярное восстановление согласованного комплекта БД/файлов/session. Определить RPO/RTO. Не запускать два gateway с восстановленной сессией.

### A07 · P2 · Echo suppression отбрасывает редактирование своих отправленных сообщений

`gateways/telegram/tg_gateway/journal.py:82`: совпадение ID с собственной отправкой подтверждает и удаляет из обработки любое outgoing-событие, без проверки event_type. Редактирование такого сообщения из официального Telegram-клиента помечается acked и не доходит до Rails; тот же фильтр применим к deleted. Воспроизведена потеря edited-события.

Исправление: подавлять только исходное received echo; edited/deleted проводить через собственную идемпотентность и связь с source_id сообщения.

### A08 · P2 · Нет ограничений роста файлов/логов и полноценного контроля pipeline

В обследованных контейнерах Docker logging — `json-file` без max-size/max-file; лимиты RAM/PID не заданы. Файлы медиа и журналы копятся, политика очистки обработанных InboxEvent/operations не определена. Нормальные ACK не удаляют скачанные файлы gateway. На момент среза свободно около 90 GB диска и 2.5 GB доступной RAM; это запас, а не защита от роста.

Web/Redis/DB healthchecks есть. Но health gateway проверяет только наличие account_id, а не фактическое состояние соединения; Sidekiq health — наличие процесса, у Python workers своего healthcheck нет. Поэтому HTTP healthy не устанавливает отсутствие зависшей/мёртвой очереди.

Исправление: ротация, дисковые/памятные лимиты с тестом нагрузки, срок хранения и безопасный GC, heartbeat workers, метрики возраста/размера очереди, unknown/dead, reconnect и аварийные уведомления. Содержимое клиентских сообщений в метрики не включать.

### A09 · P2 · Плашка CRM может остаться unlinked после успешной фоновой привязки

`chatwoot/app/javascript/dashboard/components/corporate/CrmBanner.vue:81`: периодический refresh вызывается только для pending/sending/unknown. При открытии нового исходящего чата первый GET может успеть вернуть unlinked до окончания фонового resolve. Последующая запись CRM не инициирует обновление плашки; она продолжает показывать ввод номера до перезагрузки/повторного открытия.

Подтверждено трассировкой кода; отдельный браузерный прогон именно этой гонки не выполнялся. Исправление: явное событие изменения CRM или ограниченный polling unlinked при автоматическом lookup с конечным статусом; добавить тест медленного resolve и навигации между чатами.

### A10 · P2 · Эксплуатационная документация смешивает baseline и рабочую реализацию

`docs/security.md` всё ещё утверждает, что изоляции нет и проверки впереди; `docs/operations.md` содержит утверждения об отсутствии миграций, TLS и собственной сборки. Поздние дополнения противоречат этим абзацам. `docs/evidence/server-backup.json` отражает старую копию; более новые отчёты лежат внутри backup-каталогов, а не автоматически обновляют этот файл.

Исправление: выделить исторические отчёты и один актуальный runbook; формировать свежую сводку после backup/deploy. Не выдавать старый evidence за проверку последнего состояния.

## Что подтверждено положительно

- Рабочие файлы сверены с manifest + updates: 9136 файлов, расхождений нет на момент проверки.
- В проверенных 34 штатных Rails-сценариях работают бизнес-роли, ownership, ограничения API, файлов и realtime, shared intake и CRM binding.
- DB/Redis/gateway не опубликованы в интернет; proxy опубликован на loopback. Внешний nginx завершает TLS и закрывает `/internal/`.
- `.env`/session-файлы имеют 0600, каталоги secrets/backups — 0700. Пароли/Telegram session не выводились и не переносились в тесты.
- В рабочем stack 10 сервисов, проверенные healthchecks зелёные, перезапуски контейнеров на момент среза — 0. Используется CE; Enterprise в сборку не включается.
- Обратная смена ответственного CRM имеет проверку UUID и версии локального назначения, а outbound unknown не отправляется вслепую повторно.

## Зависимости

Сверены 1531 package/version из lock-файлов PyPI/RubyGems/npm через OSV. Lock-scope включает dev/build, поэтому совпадение версии не равно эксплуатируемой production-уязвимости. В [машинном отчёте](evidence/audit-dependencies-2026-11-25.json) — 39 пакетов с доступными на дату аудита advisory; часть подробных запросов завершилась сетевыми ошибками. Неуточнённые ID перечислены в details_errors, их нельзя считать проверенными или безопасными. OS-пакеты образов отдельным сканером не проверялись.

Devise 4.9.4 отдельно проверен по первичным advisory: для [гонки Confirmable](https://github.com/heartcombo/devise/security/advisories/GHSA-57hq-95w6-v4fc) уже есть upstream workaround в `User:246`; [Timeoutable redirect](https://github.com/heartcombo/devise/security/advisories/GHSA-jp94-3292-c3xv) требует модуля, не включённого у User. Эти совпадения не объявляются двумя открытыми уязвимостями приложения.

Для [Vue I18n advisory](https://github.com/intlify/vue-i18n/security/advisories/GHSA-83rm-6c8r-g728) требуется достижимый небезопасный HTML-путь; подтверждённый exploit в этом аудите не получен. Обновление зависимостей требует проверки потребителей, не массового автоматического bump. Базовая версия CE 4.20.1 соответствует опубликованному [security maintenance release](https://github.com/chatwoot/chatwoot/releases/tag/v4.20.1); это не закрывает дефекты собственного адаптера.

Ранее пройденные браузерные сценарии не объявляются повторёнными в этом аудите. Вывод ограничен описанными поверхностями и evidence.

## Очередность исправления

1. A01/A05: надёжный приём текста и вложений, durable envelope и восстановление после сбоя.
2. A02/A03: независимый отзыв доступа и карантин для каждого пути загрузки.
3. A04: справедливые очереди и reconciliation без голодания новых сообщений.
4. A06: автоматический независимый backup и проверка восстановления после новых миграций.
5. A07–A10: редактирование, мониторинг/retention, CRM UI и актуальный runbook.

До закрытия P1 не следует расширять эксплуатацию и считать текущие зелёные healthchecks достаточной приёмкой.


Исправления и результаты повторных проверок: [audit-fixes-2026-11-25.md](audit-fixes-2026-11-25.md). Исходные находки выше сохранены как историческое свидетельство. A06 исключён владельцем.
