# Подготовка входа MAX Personal — 25.11.2026

На https://mess.prav-buro.ru установлен выпуск max-auth-20261125. 12 сервисов healthy. В разделе технического администратора «Каналы» доступно «Подключение личного MAX — тест». Владелец подтвердил тестовый аккаунт, доступ к телефону и второго собеседника. Реальная авторизация MAX ещё не подтверждена; M01–M11 остаются непроверенными до живых испытаний. Подготовленный экран не означает готовность полного MAX-канала.

SDK: maxapi-python/PyMax 2.5.0, MIT; commit c4cb917d354a1179be625925530d72c8aaa969ff. Все 188 Python-файлов установленного пакета совпали с зафиксированным исходником. Зависимости закреплены хешами. Проверка охватывает контур авторизации, хранения session и логирования, без заявления полного аудита SDK или официального одобрения MAX.

Изоляция: отдельный gateway, внутренний service token, закрытый порт, отдельная egress-сеть и secrets/max. QR/2FA доступны только техническому администратору первичного аккаунта. Менеджер, руководитель и администратор другого аккаунта не получают доступ. Ответы no-store. QR отображается локальным SVG без внешнего сервиса; пароль не пишется на диск и очищается из формы. SDK-логи не выводятся, телеметрия выключена, новый вход после отзыва сессии требует явного действия администратора. Повторный Start не создаёт параллельную сессию; устаревшее окно не может отправить пароль или остановить новый вход.

Нет маршрутов /send, /events, истории и передачи MAX-сообщений в Chatwoot, CRM или AI. При login/sync SDK может получить сведения о чатах в оперативной памяти, но они не экспортируются и не записываются как клиентская переписка. Пустой запуск и GET статуса не начинают авторизацию. После успешного входа подготовлено восстановление сохранённой session; фактически его проверяем только после сканирования владельцем.

Проверки: 13 unit tests MAX-шлюза; 35 Django tests; 53 корпоративных Rails specs. После рефакторинга повторно прошли 4 целевых request specs MAX. Ruby lint: 4 файла без замечаний; JS: 0 ошибок, 3 предупреждения. Chrome mock: 8 проверок, включая сохранение вводимого пароля при опросе статуса. Публичный HTTPS smoke: 11 проверок — доступ технического администратора, отказ руководителю, no-store, реальный экран, сохранение Telegram и workers, отзыв тестовых web-сессий. Реальный QR при smoke не запрашивался и аккаунт MAX не использовался. Хеш драйвера в серверном образе совпал с тестовым исходником, каталог session приватный.

Приватные evidence: max-auth-browser-2026-11-25.json, max-auth-production-2026-11-25.json, max-auth-production-browser-2026-11-25.json. В GitHub публикуются код и процедуры, без QR/session/паролей/evidence. Обычный Telegram gateway не перезапускался, новых миграций БД нет, backup-процедуры не менялись. Существующий backup не расширен на тестовую MAX-session; для этого этапа допускается повторный вход после потери session.

Следующие действия: владелец сканирует QR тестовым аккаунтом; проверяем M01, затем перезапуск только max-gateway и M02. После этого готовим обмен исключительно с выбранным тестовым собеседником и проверяем текст, медиа, правки, дедупликацию, reconnect и неопределённые исходы отправки. Только результаты PoC позволяют принимать решение о боевой интеграции MAX.
