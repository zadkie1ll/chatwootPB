# Веб-уведомления

Справа в верхней панели менеджера и руководителя находится кнопка «Уведомления». Подключение выполняется пользователем: «Включить уведомления» → разрешить запрос браузера → «Отправить тест» → после фактического показа нажать «Уведомление вижу». Разрешение и подписка отдельные для каждого браузера, устройства и адреса сайта; рекомендуется подключать тот адрес, которым сотрудник пользуется постоянно.

## Что проверяет индикатор

- HTTPS и наличие Notification, Service Worker, PushManager.
- Разрешение сайта в браузере и подключение к интернету.
- Сохранённую на сервере подписку текущего пользователя и действующую сессию входа.
- Принятие теста push-службой, затем подписанное подтверждение Service Worker после успешного `showNotification`.
- Явное подтверждение сотрудника, что тест действительно виден.

Зелёный статус означает выполненные проверки, а не постоянную гарантию показа всех будущих уведомлений. Отображаются время получения теста и сведения об ошибке. При отказе браузера, проблеме сети, остановке Service Worker, истёкшей сессии или подписке даётся объяснение. Проверка повторяется при возврате на вкладку/онлайн и раз в минуту; тест опрашивается до 30 секунд. Нативные операции подключения ограничены по времени. Отключение сохраняется в этом браузере и не отменяется автоматическим переподключением.

Сайт не может прочитать настройки «Не беспокоить», системное разрешение показа уведомлений или гарантировать работу браузера после полного закрытия/при ограничениях ОС. Поэтому подтверждение видимого теста остаётся действием человека. На iPhone/iPad Web Push требует запуска веб-приложения с экрана «Домой»; разрешение запрашивается после нажатия пользователя. См. [Apple Web Push](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [WebKit: iOS/iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API).

## Доставка и доступ

Новые публичные входящие сообщения Telegram/MAX ставят `Corporate::PushMessageJob` после фиксации сообщения. Отправка выполняется в очереди `low`, с повторной проверкой текущего доступа: собственные чаты, вручную общие, чаты отсутствующего сотрудника и общие неназначенные согласно существующей политике. Чужие приватные чаты, отключённые сотрудники и технические администраторы исключены. После выхода из аккаунта привязанная к этой сессии подписка больше не используется.

В системном уведомлении нет имени клиента, текста сообщения, телефона или вложений: только «Новое сообщение» и переход в приложение по исходному HTTPS-адресу. Открытие ссылки требует обычной авторизации и проверки доступа. Уже показанное ОС уведомление технически нельзя отозвать; содержимое в нём поэтому общее. Теги объединяют уведомления одного чата. Сбой одной подписки не прерывает отправку другим; неизвестный транспортный результат может повторяться с тем же тегом. Три попытки, HTTP-таймауты по 5 секунд, TTL у провайдера один час. Сетевых вызовов под общим account lock нет.

Общие штатные push Chatwoot по-прежнему отключены в корпоративном режиме. Используется отдельный путь с политикой доступа; email и мобильные push-relay не включаются. Сообщения мессенджеров не зависят от успешного показа системного уведомления.

## Сервер

Новых библиотек, таблиц и платных компонентов нет. Используются существующие `NotificationSubscription`, WebPush и VAPID-ключи инсталляции. Ключи не ротируются при обновлении. Добавлены переменные:

```dotenv
CORPORATE_BROWSER_PUSH_ENABLED=true
CORPORATE_PUSH_ORIGINS=https://mess.prav-buro.ru,https://mess.prav-buro.ru:18443,https://162.248.166.241:18443
CORPORATE_PUSH_SUBJECT=mailto:notifications@prav-buro.ru
```

Сервер должен иметь исходящий HTTPS к push-службам браузеров. Разрешены endpoint-хосты FCM, Mozilla, Apple Web Push и Windows Push; произвольные URL/локальные адреса отвергаются. Подписка связана с account, пользователем, origin и клиентом авторизованной сессии. Endpoint и криптографические параметры не возвращаются статусом и фильтруются в логах.

Публичные исключения SurfaceGate ограничены GET/HEAD `/sw.js` и POST `/api/v1/corporate_push_receipts`. Последний принимает только короткоживущий подписанный тестовый токен, проверяет текущий test_id и активную сессию, ничего не раскрывает в ответе. Остальные новые действия находятся под обычным account/API guard. Успешный receipt подтверждает вызов браузера, но не человеческое восприятие уведомления.

Для отключения отправки установить `CORPORATE_BROWSER_PUSH_ENABLED=false` и пересоздать web/worker. Подписки сохраняются. При полном откате образа сначала отключить функцию на текущем коде и дождаться завершения её задач в очереди `low`; не удалять очередь сообщений целиком. Ротация VAPID потребует переподключения браузеров. Текущий выпуск: `notifications-diagnostics-product-20261127`, предыдущий рабочий UI: `interface-scale-product-20261127`.

## Проверки

106 корпоративных Rails-примеров прошли; дополнительный набор из 11 push-примеров включает реальное шифрование Web Push через существующий gem с подменой только HTTP-провайдера, ответ 410, отзыв общего доступа и сбой отдельной подписки. 43 Vue/Service Worker теста прошли; они проверяют разрешение, отсутствие автоматического запроса разрешения, состояния без ложного успеха, позднюю ошибку провайдера, отказ Native PushManager, порядок showNotification/receipt и запрет стороннего URL перехода.

Браузерная проверка на рабочем HTTPS: вход менеджера, панель, статус без подписки, новый `/sw.js`, отказ поддельному receipt, явная ошибка вместо ложного зелёного статуса. В автоматическом профиле настоящий `PushManager.subscribe` отклонён браузером: AbortError «Registration failed - permission denied» при Notification.permission=granted и корректном публичном ключе длиной 65 байт. Это не подтверждение работоспособности реальной push-доставки на пользовательском устройстве. Для окончательной проверки требуется пользовательский видимый тест. Тестовые браузерные сессии отозваны; клиентские сообщения не отправлялись.
