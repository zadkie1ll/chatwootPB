# Эксплуатация корпоративного мультимессенджера

Рабочий адрес: https://mess.prav-buro.ru. Сервер: SSH alias `fornex.pravburo`, каталог `/opt/pravburo-chatwoot`, Compose project `pravburo-chatwoot`. Используются Chatwoot Community Edition и собственные изменения; Enterprise исключён. Telegram Personal и MAX Personal активны. MAX использует собственный шлюз на закреплённом PyMax 2.5.0.

Сведения о первоначальном лабораторном baseline находятся в `stage-1-report.md`; они не являются инструкцией для рабочего сервера. Текущая пользовательская инструкция — [bitrix24.md](bitrix24.md), состояние версий и проверок — [current-status.md](current-status.md).

## Сервисы и сеть

Сервисы: PostgreSQL, Redis, Chatwoot web/Sidekiq, private nginx, Telegram gateway, Django web, delivery worker, CRM worker, ClamAV. Наружу из Compose опубликован только `127.0.0.1:8088`; хостовый nginx завершает HTTPS и закрывает `/internal/`. Сертификат продлевает certbot.timer. Не изменять другие приложения или nginx vhost на общем сервере.

```bash
ssh fornex.pravburo
cd /opt/pravburo-chatwoot
bash scripts/compose.sh config --quiet
bash scripts/compose.sh ps
```

Полный `compose config`, `.env`, session, API/webhook токены и содержимое переписки не выводить в логи/отчёты. Для диагностики использовать только коды ошибок и обезличенные счётчики. Ротация Docker-логов ограничена настройками Compose, ограничения памяти/PID заданы по сервисам и не резервируют ресурсы у остальных приложений.

## Приём и доставка

Telegram-сессия и SQLite-журнал лежат в приватном `secrets/telegram`; процесс gateway один, проверяется файловой блокировкой. Входящий envelope и задача медиа фиксируются до скачивания. Текст и статус медиа могут поступать отдельно. Неуспешная загрузка/передача сохраняется для повторной обработки; другие чаты продолжают обрабатываться. Получение сохранённого envelope Django и завершение его обработки в Chatwoot подтверждаются отдельно.

`pending` — ещё не отправлено; `in_flight`/`sending` — запрос выполняется; `sent` — платформа подтвердила; `failed` — известный отказ; `unknown` — исход не доказан. Не переводить unknown в pending вручную: сначала сверить журнал и реальный результат. Новые отправки и reconciliation обходятся независимо с курсорами.

Редактирование использует отдельную операцию с UUID/версией и Telegram editMessage. До подтверждения в чате сохраняется прежний текст. При ошибке Telegram исходный текст не заменяется локальной выдуманной версией. Передача клиента отменяет ещё не отправленные операции; неизвестный результат блокирует передачу, но **не блокирует отзыв доступа сотрудника**.

Ограничения: поддерживаемые вложения до 20 MiB; TTL/самоуничтожаемые материалы и запрещённые типы показываются как недоступные. Скрытые телефоны не угадываются. Статусы delivered/read не имитируются. Восстановление старой истории целиком не является импортом всех Telegram-диалогов.

## Проверка файлов

Любые пользовательские вложения, включая внутренние заметки и direct uploads, проходят карантин. Скачивание/preview закрыты до проверки типа содержимого и ClamAV. При недоступности сканера файл остаётся закрытым и повторно проверяется. Входящие из Django перед сохранением также проверяются; отказ файла сохраняет текст и отображает ошибку.

Перед активацией карантина старые attachments ставятся на проверку. Локальный антивирусный EICAR probe не отправлять в клиентский Telegram. Временные медиа gateway удаляются только после подтверждения обработки и безопасного интервала; незавершённые события не удаляются. Журналы сохраняют минимальные ключи идемпотентности и индексы удаления, очищая обработанные payload по сроку хранения.

## Состояние обмена и задержки

У руководителя отображается предупреждение о задержке обмена. Endpoint `corporate/health` доступен только руководителю и показывает состояние Telegram, workers и возраст очередей без имён клиентов/текста. Фоновые процессы имеют heartbeat; Sidekiq дополнительно проверяется через его heartbeat/очереди. Зелёный nginx `/health` отдельно не доказывает доставку.

При задержке проверить `compose ps`, heartbeat, число/возраст pending/unknown, связь gateway, ClamAV, свободное место/RAM и наличие ошибок БД. Не выполнять глобальную очистку Docker. Перезапуск только нужного сервиса сохраняет named volumes. Повторный запуск gateway с той же session параллельно запрещён.

Исторические сбои вложений прежнего gateway можно поставить на восстановление командой `python3 scripts/server/recover-telegram-media.py` **только при остановленном telegram-gateway**, затем снова запустить его. Скрипт не экспортирует переписки и не отправляет клиентских сообщений.

## CRM

Секреты подключения находятся только в серверном `.env`. Настройка полей выполняется `scripts/server/configure-bitrix.py`; флаг `--messenger-fields` переименовывает согласованные прежние текстовые поля, не удаляя значения, и создаёт URL-поля «Мессенджер» для лида/сделки. Ключи `BITRIX_MESSENGER_FIELD`/`BITRIX_LEAD_MESSENGER_FIELD` задают эти поля.

При поиске по телефону предпочтительна последняя открытая сделка; при её отсутствии — последний открытый лид. Явная ссылка выбирает конкретную карточку. После конвертации связанного лида приложение ищет открытую сделку с его LEAD_ID и переносит привязку, сохраняя старый URL лида действительным переходом в тот же защищённый чат. Ответственного берёт из CRM, не запускает цикл встречных назначений.

Пересинхронизация URL для старых привязок должна выполняться без принудительной смены ответственного (`assign_owner: false`). Нельзя создавать тестовые сделки на рабочем портале: это может запустить реальные автоматизации.

## Обновление и откат

Собрать и проверить образы локально для Linux/amd64; на рабочем сервере frontend не компилировать. Перенести архивы без secrets/Enterprise, сверить SHA и source manifest. Зафиксировать предыдущие образы и приватную конфигурацию; остановить writers только этого проекта, выполнить миграции Rails/Django, поднять согласованный комплект web/worker/gateway/integration и выполнить smoke.

Новая модель хранит несколько версий операций на сообщение. **После появления edit-операций откат к старому коду доставки отдельно от данных небезопасен:** старый код может трактовать их как новые отправки. При такой аварии остановить внешнюю доставку и применять совместимое исправление либо восстанавливать согласованный комплект состояния. Не выполнять down -v.

## Резервные копии — исключены из текущего исправления

По решению владельца A06 не исправляется в этой итерации. Существующий ручной `python3 scripts/server/backup.py --verify-restore` сохраняет БД, файлы, Redis и защищённую session на том же сервере и проверяет восстановление БД в отдельных временных базах. Отчёт конкретной копии находится в `backups/<timestamp>/report.json`; старый `docs/evidence/server-backup.json` не является гарантированно свежим отчётом.

Расписание, внешнее защищённое хранение, retention копий и RPO/RTO остаются открытыми. Восстановленную Telegram session не запускать одновременно с исходной. Производственные копии не переносить в dev/staging.


## Сводка OpenAI

Ключ хранится только в приватном `secrets/openai/api-key`, каталог 0700 и файл 0600, и монтируется read-only в Rails: `/run/secrets/openai/api-key`. Он не входит в ENV браузера, публичные настройки или GitHub. При смене ключа обновите файл на сервере; перезапуск не требуется. После полного восстановления сервера этот отдельный секрет нужно восстановить/настроить отдельно; существующая автоматизация backup в рамках задачи не менялась.

Модель для `corporate_summary` выбирается через `config/llm.yml` и `Llm::FeatureRouter`; используется Responses API, `store: false`, без tools и автоматических повторов. На пользователя разрешён один запрос в 45 секунд. Права проверяются до запроса и повторно перед выдачей результата. Технический администратор и менеджер чужого клиента не могут вызвать сводку. Ответ OpenAI не сохраняется как сообщение и не отправляется в мессенджер.

Rails сохраняет сеть без выхода в интернет. Сервис `openai-proxy` имеет отдельный egress и пропускает только POST `/v1/responses` к фиксированному `https://api.openai.com`, с проверкой TLS-сертификата. Он не публикует порт на хосте и не пишет access log. Остальные пути закрыты. Для backend-only патча используется Dockerfile.backend-patch от проверенного CE-образа с теми же frontend assets; полная сборка из исходников остаётся основной процедурой.


## Выпуск MAX Personal 25.11.2026

Текущая совместимая связка: CW `max-product-20261125`, integration `max-delivery-20261125`, gateway MAX `delivery-20261125-final`. Telegram gateway сохраняет `reliable-20261125`. MAX_DELIVERY_ENABLED=true, MAX_CRM_ENABLED=true, CORPORATE_MAX_INBOX_ID указывает отдельный API inbox. Пустые MAX_TEST_PEER_IDS и MAX_TEST_PHONE означают полный режим. Внутренний MAX_GATEWAY_TOKEN и session остаются только в приватных файлах сервера.

Канал создаёт `scripts/server/activate_max.rb`: запуск через Rails runner возвращает ID inbox для CORPORATE_MAX_INBOX_ID. `scripts/server/prepare-max.py` подготавливает секрет и профиль max-poc, но самостоятельно не авторизует аккаунт и не включает доставку. Вход и 2FA выполняет технический администратор в «Каналы». После проверки сессии и тестового обмена оператор включает флаги доставки/CRM и применяет конфигурацию согласованной связкой образов.

MAX journal: `secrets/max/delivery.sqlite3`, WAL/FULL. SDK session хранится рядом, один процесс-владелец защищён файловой блокировкой. Не открывать второй SDK с той же session. Доступный сокет не равен авторизованному аккаунту. Неизвестные отправки сверяются по CID/внешнему ID, автоматически повторять их нельзя. `/diagnostics` возвращает метаданные только в ограниченном режиме испытаний; в полном режиме чужую историю не выдаёт.

Нельзя откатывать только integration на Telegram-only образ, пока web отдаёт MAX outbox: старый worker не различает каналы. Использовать согласованные версии, поддерживающие MAX, либо отдельно остановить MAX-доставку и сверить её незавершённые операции перед откатом. Сессии и клиентские volumes не удалять. Изменения БД Chatwoot/Django этому выпуску не нужны.

Несколько файлов MAX разделяет интерфейс: одна доставка на файл. Смешанный внешний payload фото+документ MAX отвергает как proto.payload. Прямой API не принимает такой пакет; его отказ не считается успешной доставкой. Медиа проверяется по реальному типу и ClamAV. Офисные форматы Apple разрешены, HTML/SVG остаются запрещены. Завершённые события/файлы gateway очищаются через 30 дней, незавершённые сохраняются.

Процедуры backup по указанию владельца не менялись. Прежний backup не включает MAX session; после её потери потребуется повторный QR-вход. Ограничения и доказательства живых проверок: [MAX delivery](max-delivery-2026-11-25.md).
