# 0008. Идентичность сотрудников и дальнейшее объединение приложений

Статус: текущий каталог реализован; конкретные внешние приложения и общий вход требуют отдельного согласования контрактов.

## Решение сейчас

Локальная идентичность сотрудника — неизменяемый `User.id`; организационные права задаёт `CorporateMembership(account_id, user_id)`. Для внешнего обмена пару `account_id + user_id` нужно хранить вместе с идентификатором исходной системы. Имя, почта, рабочий URL и Bitrix ID не являются универсальными идентификаторами человека. При изменении имени/почты локальный ID и принадлежность клиентов сохраняются.

Bitrix24 остаётся отдельной внешней привязкой (`CorporateCrmEmployee`), а не системой авторизации. Совпадение email само по себе не объединяет людей между приложениями. При нескольких порталах понадобится учитывать идентификатор портала вместе с внешним ID. Каталог имеет явную версию API и серверные границы account/роли; legacy-контракты не меняются.

## Следующий шаг после перечня приложений

1. Описать для каждой системы источник сотрудников, локальные ID, роли, порядок блокирования, текущую аутентификацию и API.
2. Выбрать владельца общей идентичности и способ единого входа. Подключать каждое приложение отдельным клиентом, с отдельными правами; не передавать общие cookies, пароли или администраторский токен между приложениями.
3. Хранить явное соответствие подтверждённого внешнего subject локальному пользователю. Сохранить существующие User ID и ownership, не пересоздавать менеджеров при подключении общего входа.
4. Оставить локальную авторизацию доступа к клиентам и файлам. Общий вход сам по себе не выдаёт права руководителя и не открывает переписки другим приложениям.
5. Для межсервисного обмена определить отдельные ограниченные полномочия, версию событий, идемпотентность и аудит. До этого каталог требует штатных прав руководителя; отдельные service credentials и внешние webhook не создаются.

Решение не требует Enterprise или общей базы данных приложений. Текущая работа не меняет вход сотрудников и не подключает неизвестные внешние системы. Привязка к единому входу не должна зависеть от того, использует сотрудник основной домен мессенджера или резервный HTTPS-вход.
